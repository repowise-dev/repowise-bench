# G4 in TypeScript: an oracle with a call model, and what validating it changed

**Status: measured on two repositories, one cell each, three arms.** The
[preregistration](PREREGISTRATION.md) predicted this cell was the least likely
to survive. It survived, but only after validation found two defects large
enough to invert the reading.

## Why not scip-typescript

The preregistration named `scip-typescript` and named the risk in the same
breath: SCIP has no call-edge model. It records occurrences, so turning "a
reference to X appears inside Y" into "Y calls X" is a fold we would have to
write, and a fold we write is an instrument we grade ourselves against. That is
the defect G4 exists to remove, so importing it at the front door was never
going to work.

The oracle is the `tsc` type checker instead, and two facts come from the
compiler rather than from us:

* **that a node is a call.** The AST says so. `CallExpression`, `NewExpression`
  and `TaggedTemplateExpression` are call syntax, not an inference about a
  reference sitting near a parenthesis.
* **what it calls.** `checker.getResolvedSignature` returns the signature the
  compiler type-checks the site against, with the type information a real `tsc`
  build has.

What stays ours is what stayed ours in Go: the declaration position a function
is keyed at. It is validated the same way, and this time the validation mattered.

### What the oracle analysed

| cell | files | oracle edges | functions judged | unjudged share, per arm |
|---|---:|---:|---:|---|
| zod (no tests) | 116 | 1269 | 753 | repowise 46%, CodeGraph 34%, codebase-memory-mcp 35% |
| hono (no tests) | 185 | 706 | 480 | repowise 16%, CodeGraph 37%, codebase-memory-mcp 32% |

Nothing is bold, and that is the result. **We are the most precise arm in both
cells and we separate from neither.** Against CodeGraph the gap is decisive in
both cells, 0.992 against 0.729 and 0.977 against 0.805. Against
codebase-memory-mcp the intervals overlap in both, so both are ties and are
reported as ties. Recall is a tie everywhere except zod against CodeGraph.

This is a weaker result than the Go cell, where we were most precise in all five
and separated from codebase-memory-mcp in every one. **TypeScript is where that
tool catches us.** The two languages should be read together rather than
separately: it is the least precise arm in Go by a wide margin and our equal
here.

## What validation changed, which is the point of doing it

The first run of this cell put us at 0.698 and codebase-memory-mcp at 0.620.
Both numbers were artefacts. The modal declaration-line offset was `(0, 0)` in
that run, exactly as it is now, which is precisely why the offset check is not
sufficient on its own: matched edges are by construction the ones that agree, so
a defect that only affects unmatched edges cannot show up in it.

**Caller granularity.** `tsc` attributes a call to the innermost containing
function. In TypeScript that is a callback inside `lazy(() => ...)`, a
`get error()` on an object literal being returned, a local
`const handleParsed = ...` inside a method. No arm here gives any of those a
symbol, so every such edge was scored wrong for all three. Attributing instead
to the **outermost named function** containing the call site moved every arm at
once: ours from 0.698 to 0.962, codebase-memory-mcp's from 0.620 to 0.970.

This is a granularity decision, and it is the same one the Go cell already makes
when it refuses call-site keying because one arm stores no call-site line. It
costs real information, since two sibling helpers inside one exported function
collapse into a single caller, and that cost is paid identically by every arm.
The alternative is a rate that partly measures nesting depth.

**`new X()` resolving to an inherited constructor.** A class that declares no
constructor of its own resolves to a base class constructor, so the oracle
pointed the edge at a class the code never names. Which entity is constructed is
a different question from which signature type-checks the site, and a call graph
is asking the first. The class symbol comes from the checker either way.

## Identities, confirmed by hand

Protocol step 2, on zod: **20 of 20 declaration positions are correct**, drawn
seeded from the 885 the oracle asserts. Full draw and verdicts in
[`identity-validation-zod.json`](identity-validation-zod.json); the Go draw and
the method are in [`identity-validation.md`](identity-validation.md).

The draw also found something about us rather than about the oracle. At seven of
the twenty positions both peers hold a symbol and **we hold none**:

| shape | example |
|---|---|
| a `function` declared inside an arrow | `packages/zod/src/v4/locales/de.ts:13` |
| a `static create = (...) => {}` class property | `packages/zod/src/v3/types.ts:2060` |
| a `const` arrow declared inside a function body | `packages/zod/src/v4/core/to-json-schema.ts:279` |

These are callee identities, so each one is recall we cannot earn: an edge into
a function we never gave a symbol to can never be matched. It does not touch
precision.

One position, a method on an object literal built inline in a `return`, is held
by no arm at all. Like the Go cell's function literal, it can never match for
anyone and moves nobody's number.

## The hand-graded cell, and why only half of it is corroborated

[G1](../g1-edge-precision/) graded TypeScript by hand on zod at 30 rows per
side: repowise 29/30 = 96.7%, CodeGraph 7/30 = 23.3%.

**Ours reproduces.** The checker, over roughly 1,650 edges instead of 30 rows,
says 99.2%, inside the hand grade's interval of [83.3, 99.4].

**CodeGraph's does not**, and the reason is population rather than method.
`packages/zod/src/v3/tests/Mocker.ts` receives **3,215 of its 13,032 zod call
edges**, a quarter of its entire call graph on this repository pointing into one
test double. That file is test code, so the no-tests variant scopes it out, and
what remains reads 72.9%. The hand audit sampled the full edge set and met that
class; this cell does not. **So this page corroborates the hand-graded number
for two arms and cannot speak to CodeGraph's**, which is a limit of the cell and
not a correction to G1.

## The with-tests variant is void, and is reported rather than dropped

Both repositories were also run with test files included, and both are unusable
for the same reason: a test file imports its own package by name, and the
repository's dependencies are not installed, so `tsc` cannot resolve the call.
On zod that is 12,777 of 33,237 call sites, on hono 12,033 of 34,969, in both
cases roughly a third. Every unresolved site withholds its caller.

zod with tests was carried through to rates, in
[`zod-tests-g4.json`](zod-tests-g4.json), purely to show the size of the
problem: the unjudged bucket is 72% of our emitted edges and 76% of CodeGraph's.
The preregistration says an oracle that cannot cover enough of the program
becomes recall-only rather than being quietly rescoped, and a bucket that size
is past that line, so **neither with-tests cell is quoted anywhere on this
page**. hono with tests was stopped at the oracle, since a third of its call
sites being unresolvable settles it without computing a rate nobody should read.

Installing each repository's dependency tree would fix this. It has not been
done, and it is the obvious next move for this cell.

## What the oracle declines to judge

A function containing any call site the checker cannot take to a real
implementation is withheld from the reachable set, so its unmatched edges land
in `unjudged` and not in `contradicted`. This matters more here than in Go, and
in the opposite direction: RTA over-approximates by devirtualising, while `tsc`
under-approximates, resolving a call through an interface, an abstract member or
a function-typed value to the *declared* signature. On hono that is 30% of
in-repo call sites. An arm that resolved such a call to the concrete function is
more useful than the oracle, not wrong, and must not be charged for it.

The cost is a large unjudged bucket, 16% to 46% of emitted edges depending on
arm and cell. It is reported at full size and charged to nobody.

## Limits

* **Two repositories, one cell each.** Not a TypeScript claim at corpus scale.
* **Each cell is scoped to the library's own source tree**, `packages/zod/src`
  and `src`. A monorepo's documentation site and benchmark harness pull in
  dependencies the library does not have, and type-checking them without an
  install produces unresolvable sites that withhold callers wholesale. Both
  sides are restricted to the same set, so no arm is charged for what is outside
  it.
* **`contradicted` is strong evidence, not proof**, exactly as in Go.
* **Recall is not comparable across rows** here either.
* The oracle skips JSX element instantiation, which no arm emits as a call
  either. Both cells are scoped so that this count is zero.

## Reproduce

```bash
cd graph/experiments/g4-oracle-anchored/oracle-ts
npm install                     # typescript, pinned in package.json
node oracle.mjs -repo <repo> -subdir <src-dir> [-tests] [-diagnose] -out cell.jsonl
cd ..
python compare.py --oracle oracle-ts/cell.jsonl --repo <repo> --repo-name <name> --out cell-g4.json
python render_g4.py zod-notests-g4.json hono-notests-g4.json
```

`-diagnose` reports why call sites went unresolved, which is what identified the
dependency problem above rather than leaving it as a guess.
