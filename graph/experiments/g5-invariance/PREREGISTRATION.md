# G5: does the resolver resolve, or does it match names?

**Written before any G5 run.**

## Why this experiment exists

Precision and recall both reward a resolver that guesses well on the repositories
in the corpus. Neither one distinguishes a resolver that understood the program
from a resolver that matched an identifier and got lucky, because on ordinary
code those two produce nearly the same graph.

G5 separates them with mutations: small, mechanical, semantics-preserving or
semantics-known edits to a real repository, where a resolver that understands
scope gives a predictable answer and a name-matcher gives a different, also
predictable, answer. Neither requires a gold graph. Both are cheap and
deterministic.

We already know this will score us badly in one place, which is the point. Our
Java path mints a receiver-less twin of every member call and binds it by bare
name. Mutation 1 is designed to catch exactly that, and it will.

## The mutations

Each is applied to a checkout, the graph is rebuilt, and the edge set is compared
to the unmutated baseline.

**1. Decoy twin.** Add a new file declaring a function with the same name as an
existing, heavily-called one, in a module nothing imports. Semantics unchanged:
no call site can reach it.
*Correct behaviour:* the edge set is unchanged except for the new declaration's
node. *Name-matching behaviour:* call sites gain an edge to the decoy, or their
existing edge becomes ambiguous and flips.
*Score:* edges retargeted or added to the decoy, as a share of call sites naming
that symbol. Lower is better. **This is the discriminating mutation.**

**2. Consistent rename.** Rename a symbol and every reference to it, repository
wide, to a name that appears nowhere else.
*Correct behaviour:* the edge set is isomorphic to the baseline under the
renaming. *Score:* edges lost or gained. Zero is the only passing answer, and any
non-zero result is a resolver depending on something about the old spelling.

**3. Shadowing.** Introduce a local variable or parameter whose name equals an
imported symbol that is called later in the same scope.
*Correct behaviour:* the call no longer resolves to the import. *Score:* share of
shadowed sites still bound to the import. This one is a genuine open question on
our side and we do not know the answer.

**4. Overload split.** Where a language allows it, add an overload of a called
method with a different arity.
*Correct behaviour:* existing call sites keep their original target. *Score:*
share of call sites that flip. Both tools are known to be overload-blind, so we
expect both to score poorly, and publishing a row where we tie at a bad number is
part of the point.

**5. Vendored twin.** Copy a called module to a second path without changing any
import. *Correct behaviour:* nothing moves. This one exists because caffeine's
`guava/` subtree and zod's parallel v3/v4 trees are naturally occurring instances
of it, and both have already produced rows that looked wrong and were not.

## Protocol

* Mutations are generated by script from a seed, never written by hand, so the
  set is reproducible and so nobody can pick a flattering site.
* Both tools index the same mutated checkout. Neither is told a mutation happened.
* The unmutated baseline is rebuilt in the same session, on the same machine, and
  a baseline that does not reproduce the previous run's edge count byte for byte
  voids the run. Edge sets have already been checked for ingestion-order
  determinism, so a difference here is a real problem and not noise.
* Every mutation is applied to a scratch copy. No mutation is ever applied to a
  repository in `test-repos/`.

## Predictions

* **We fail mutation 1 on Java, badly**, at 30% or more of call sites naming the
  decoyed symbol picking up a wrong or ambiguous edge. This follows directly from
  the receiver-less twin, and if it does not happen, our understanding of our own
  Java path is wrong and that is the more important finding.
* **We pass mutation 1 on Go and C#**, under 5%, where receiver typing landed.
* **Both tools pass mutation 2 at exactly zero** on every language. If either
  does not, the resolver is keyed on something it should not be, and that is a
  bug report rather than a benchmark row.
* **Both tools fail mutation 4** at broadly similar rates. We do not expect to
  win this one.
* **Mutation 3 is the one we cannot call.** No measurement exists on either side.

## Why this is worth publishing even where we lose

A benchmark whose author already knows which cell they lose, has written the
cause down, and ships the instrument that proves it is a more credible document
than one that wins every row. Mutation 1 on Java is that cell.
